What the product is

RepoMap takes a public GitHub URL, shallow-clones the repo, runs static analysis on every Java file (javalang AST), and returns a single deterministic JSON that the Next.js frontend turns into 7 views: Overview, Architecture, Data flow, Dependencies, Entry points, Critical paths, and Health. The backend is a FastAPI streaming server; the frontend is a React/Next.js app with Mermaid diagrams. No database, no auth, no persistence — scans live in a scans/ folder on disk.

Genuine strengths to protect

  • Deterministic output. json.dumps(sort_keys=True) + no timestamps means the same repo always produces the same bytes. This is rare and valuable.
  • Embedded metadata in Mermaid strings. The %% flow\t / %% path\t / %% diagram\t comment protocol is an elegant way to ship structured data inside a diagram string without a separate API field.
  • Streaming progress. The NDJSON stream in scan-github/stream with a fallback to the blocking endpoint is solid defensive design.
  • Zero-dependency frontend data model. lib/types.ts is clean and matches the contract exactly.
  • Clean CSS architecture. Design tokens in :root, semantic class names, no inline styles in JSX. Easy to retheme.

Critical issues

Things that will break the product for real users today.

High Scans are lost on every server restart

The backend never writes scan results to disk. readScans() reads from ../../scans/ but main.py only returns the result in the HTTP response. If the user refreshes the page, all their scans are gone. The data needs to be persisted — either to scans/ from the Python side, or to localStorage in the browser.

scanner/main.py · apps/web/lib/readScans.ts
High No README — new users have no idea how to start

There is no README.md at the repo root. The contract is in contract.md (aimed at the scanner), but nothing tells a new contributor how to run the scanner, start the web app, or what the SCANNER_URL env var must be set to. This is the single biggest barrier to onboarding.

/ (root — missing README.md)
High Scanner URL is hardcoded to localhost — deployment is silent-fail

const BACKEND = process.env.SCANNER_URL ?? "http://localhost:8000" — there is no validation or startup warning when this env var is missing. In a deployed environment the frontend silently points at nothing and returns a 502 to the user with no hint about configuration.

High Streaming progress events are consumed but never shown

readScanStream() in Dashboard.tsx collects all NDJSON events, but the status progress events (phase: "clone", "scan", "overview") are discarded — the user just sees "Mapping…" with a spinner. For repos that take 30–60 seconds, this looks like the app is hanging.

Important improvements

Medium Only Spring Boot Java is supported — this is completely invisible

Any non-Java or non-Spring repo returns "Unscored" with a single generic finding, but the landing page says "Map a public GitHub repository" with no caveat. Users pasting Python, Node, or Go repos will be confused by a blank result. The constraint should be front-and-centre on the landing page.

apps/web/components/Dashboard.tsx · line 142
Medium No way to delete or refresh a scan

Once a scan is in the sidebar there is no delete or re-scan button. Re-pasting the same URL replaces it in state, but that is not obvious. Stale scans accumulate in the sidebar with no way to manage them.

apps/web/components/Dashboard.tsx · sidebar-repos section
Medium javalang parse errors are silently swallowed everywhere

Six separate except Exception: continue blocks in scan.py and overview.py mean a malformed Java file is silently skipped with no indication in the output. A file that fails parsing should appear in the findings list so the user knows the scan is incomplete.

scanner/scan.py · scanner/overview.py
Medium The "Health" churn field is always the same static string

"Only the latest commit is cloned, so the files that change most often are not in this scan." is hardcoded in overview.py. This is honest but wastes a signal card on noise. It should be removed or replaced with something actionable (e.g. git log line count from the shallow clone).

scanner/overview.py · line 84
Medium GitHub API called without a token — rate-limited to 60 req/hr

repo-meta/route.ts calls the GitHub REST API with no Authorization header. Unauthenticated requests are capped at 60/hour per IP. In a shared deployment this will fail silently for any moderate traffic. Add a GITHUB_TOKEN env var (optional, graceful degradation).

apps/web/app/repo-meta/route.ts · lines 12–13
Medium 500-file hard limit is too low for real Spring Boot monorepos

The contract caps analysis at 500 Java files, returning "Unscored" above that. Many production Spring Boot services have 200–800 files. The limit should be raised or made configurable, with per-module sub-scanning for large codebases.

User experience improvements

UX Real-time scan progress phases should be displayed

The NDJSON stream emits {"type":"status","phase":"clone"}, "scan", "commit", "overview" events. Show these as a progress stepper ("Cloning… → Scanning files… → Building overview…"). This removes the perceived hang on large repos.

apps/web/components/Dashboard.tsx · readScanStream()
UX The landing page has no example repos to try

A new user faces a blank text field with no idea what to paste. Three or four pre-filled example buttons (well-known Spring Boot repos like spring-petclinic or spring-boot-realworld-example) would dramatically reduce the first-scan friction.

apps/web/components/Dashboard.tsx · plaque section
UX Scan timestamp is missing — user cannot tell how fresh a cached result is

The commit SHA is shown but not when the scan was run. A relative timestamp ("scanned 2 hours ago") in the sidebar or overview would let users know if they need to re-scan after a push.

apps/web/components/Dashboard.tsx · sidebar-repos / OverviewBoard
UX Route selector in Data flow overflows on repos with many endpoints

The route selector is a horizontal tab strip (chart-switch) with no virtualisation or truncation. A repo with 40+ routes produces an unusably wide row. A searchable dropdown or paginated list would scale better.

apps/web/components/Dashboard.tsx · FlowSection route selector
UX No keyboard navigation between sections

The sidebar nav items are buttons with aria-current, but there are no keyboard shortcuts (e.g. 1–7 to jump to each section) and no tabindex management when the mobile sidebar closes. Keyboard and screen-reader users have a degraded experience.

Missing features that would make this genuinely useful

Feature Diff / compare two scans of the same repo

The most valuable onboarding use-case is "what changed since last sprint?" Show a diff of findings, entity count, and risk score between two scan results of the same service. The deterministic output makes this trivially computable.

Feature Shareable permalink / export

There is no way to share a scan result with a colleague. A "Copy link" or "Export JSON" button, or a simple /scans/[service] route that serves the stored scan, would make the tool team-ready. Currently the result exists only in the current browser session.

Feature Kotlin support

A large fraction of Spring Boot codebases are now Kotlin. javalang cannot parse .kt files. Adding tree-sitter or a Kotlin-specific parser for the same analysis (entities, controllers, repositories) would massively expand the addressable set of repos.

scanner/scan.py · _collect_java_files()
Feature Multi-module / multi-service support

Maven multi-module projects (common in microservice monorepos) are scanned as a flat list of Java files. A module-aware scan that maps each Maven module to its own service entry, with cross-module dependency arrows, would be far more accurate for real enterprise repos.

Feature Private repo support via GitHub token

The scanner only accepts public repos. Adding an optional per-scan GitHub PAT (passed as a header or URL param, never logged) would open the tool to teams who want to analyse their own private codebases.

scanner/main.py · _clone_and_scan()
Feature OpenAPI / REST endpoint table

The scanner extracts endpoints[] with method, path, and entity. The UI does not show a standalone API table. A filterable endpoint browser (like a lightweight Swagger view) would be useful for new team members who need to find a route quickly.

Developer experience & onboarding

DX No README — no setup instructions anywhere

A new contributor cloning this repo has to read four Python files and three TypeScript files to understand how to run anything. A root README.md with a 5-step quickstart (install Python deps, uvicorn main:app, set SCANNER_URL, npm run dev, paste a URL) is the single highest-leverage improvement.

DX No .env.example for the web app

The only env var (SCANNER_URL) is referenced in code but never documented. Add a apps/web/.env.example with SCANNER_URL=http://localhost:8000 so the required variable is self-documenting.

apps/web/ — missing .env.example
DX No tests anywhere in the project

The scanner has zero unit tests. Given that scan.py alone is ~1 400 lines of complex AST walking logic, a single wrong assumption about javalang node shapes can produce silent wrong output. At minimum: snapshot tests for the 5 finding types and the Mermaid comment format.

scanner/ · apps/web/
DX No docker-compose.yml — local setup requires manual coordination

Running the product locally requires two separate terminal windows (Python uvicorn + Next.js dev), knowing the right ports, and manually setting env vars. A single docker-compose.yml at the root (or a Makefile with a make dev target) would reduce the setup to one command.

DX contract.md is an internal spec, not user-facing documentation

contract.md documents the JSON schema for the scanner developer, but reads like a constraint list, not a guide. Move it to docs/scanner-contract.md and add a docs/architecture.md that explains the data flow: GitHub → clone → scan.py → overview.py → NDJSON → Next.js → 7 views.
